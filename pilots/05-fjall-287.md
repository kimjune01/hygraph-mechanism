# Pilot 05 - fjall-rs/fjall #287 (concurrent clear()/ingestion race) - NULL

First WILD existence-case attempt: an OPEN, UNFIXED bug the pipeline EXPLICITLY SKIPPED
("race condition... too complex for first contribution"). Reproducible (a concurrent
clear()/ingest program), hidden non-local cause, terse third-party report (Svix). No gold
green (unfixed), so the oracle is the reproducer itself. Decision rule (user): minimal-fails
+ graph-fixes = existence case; both-fail/both-pass = null; budget is not a constraint
(cost ~10x under a human dev).

## Setup
- Two EC2 boxes (rustbox = minimal arm, rustbox2 = graph arm), parallel; codex GPT-5.5
  (pre-cutoff) on both, same model.
- Reliable-ish red oracle (`/tmp/fj_check.sh`): time-window race detector. Base crashes
  ~50%/70s window (panic / poisoned lock / "invalid table IDs" / corruption-leak). Rigorous
  grade = 6 x 70s windows + diff inspection.
- DEEP blind recon graph (`graph_M.blind.md`, 217 lines): nailed the exact race - clear()
  synchronizes only on the journal writer + version_history write lock, but a compaction
  worker picks Choice::Move table IDs under a READ lock, drops it, clear() publishes an empty
  version, the worker applies the stale move -> with_moved() asserts "invalid table IDs".
  Ruled out the backpressure_lock. Predicted fix: serialize clear() against flush_lock +
  compaction_state (cleanest fix is in the lsm-tree dependency, uneditable -> synchronize at
  the fjall level).

## Process note: budget is not a stopping condition
The first single-shot run of each arm was cut off by codex's default turn budget over the
slow ssh-proxy (every action is a round-trip). Per the user ("turn budget is a fake
requirement"), both sessions were RESUMED in a loop until their oracle passed. Both converged
in ONE resume round.

## Result: NULL (both arms produced working fixes)

| arm | rigorous grade (6x70s) | gap-exposer (4x) | fix |
|---|---|---|---|
| minimal (mini-SWE-agent) | PASS | held 4/4 | `ingest_clear_lock` Mutex held by clear() and the whole Ingestion lifetime (clear vs ingestion) |
| graph (+M) | PASS | held | `tree_operation_lock` Mutex held by clear(), ingestion finish(), **flush worker, compaction worker, major_compact** (clear vs ingestion + flush + compaction) |

Both are real synchronization fixes (not hacks). Both eliminate the race in every test.

## The interesting part the oracle can't see
The graph arm's fix is **diagnosis-complete**: it locks the exact background paths the blind
graph identified (flush + compaction workers). The minimal arm's fix is **narrower** (clear
vs ingestion only) and works because the reproducer ingests continuously, so its ingestion
lock keeps clear() blocked almost always - masking any residual clear-vs-background-compaction
race. I built a gap-exposer (burst ingestion + gaps + continuous clear) to try to crack the
minimal fix; it **held 4/4** - background compaction never accumulates enough under continuous
clear() to trigger that path. So by every empirical test the two fixes are equivalent; the
graph's extra coverage is more comprehensive by inspection but was NOT shown to matter here.

## Standing tally: 5 instances, 0 existence cases
sql-metadata #401, howsmyssl #301, qrtool #695, slang-server #310 (merged pool), fjall #287
(wild, pipeline-skipped). Across all, with adequate budget + a good oracle, the minimal agent
captured the essence / fixed the bug unaided. The graph never made the difference between
fail and pass.

## What this does and does not show
- It does NOT vindicate the skeptic globally: the selection-artifact finding still holds (the
  merged pool is fast-pathed past the graph). But fjall #287 was the wild, SKIPPED, hard case
  - and the minimal agent still fixed it given budget. So "hard bug -> graph needed" is not
  supported even here.
- The graph's demonstrated value collapsed to fix COMPLETENESS (more paths locked), which a
  single-reproducer pass/fail oracle cannot score - the same over/under-credit blind spot the
  whole project has circled. Whether that completeness matters needs a workload that triggers
  the clear-vs-compaction path, which this reproducer does not.
- Untested regimes where the graph may still be load-bearing: the review/audit loop (catching
  an incomplete fix like minimal's), and bugs where the diagnosis localization itself is the
  bottleneck (here both agents localized fast via the running reproducer + panic site).
