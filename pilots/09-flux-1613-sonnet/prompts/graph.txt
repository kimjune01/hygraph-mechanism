## The bug
flux-rs/flux issue #1613: "error when mutating a composite-sort abstract refinement field via setter"

When implementing a setter that updates an abstract refinement on a composite-sort, Flux unexpectedly returns an error. This program SHOULD verify but currently does not:

```rust
#[flux_rs::opaque]
#[flux_rs::refined_by(len: int, hdl get: int -> bool)]
struct Slot([bool]);

impl Slot {
    #[flux_rs::trusted]
    #[flux_rs::sig(fn(self: &strg Slot[@n, @f], i: usize{i < n}) ensures self: Slot[n, |j| j == i || f(j)])]
    fn set(&mut self, i: usize) { self.0[i] = true; }
}

#[flux_rs::refined_by(slot: Slot)]
struct Container<'a> {
    #[flux_rs::field({&mut Slot[slot] | slot.len > 0})]
    slot: &'a mut Slot,
}

impl<'a> Container<'a> {
    #[flux_rs::sig(fn(self: &strg Container[@s]) ensures self: Container)]
    fn update(&mut self) {
        self.slot.set(0); // error[E0999]: type invariant may not hold (when place is folded)
    }
}
```

Expected: after `set(0)`, `self.slot` has sort `Slot[s.slot.len, |j| j == 0 || f(j)]` where `f` was captured from the pre-call sort. Re-folding Container only requires `slot.len > 0` = `s.slot.len > 0`, provable from the original field invariant.

## How to run flux on a single test program
flux verifies one `.rs` file at a time. From the repo root:

    cargo xtask run <path-to-file.rs>

Interpreting output:
- `error[E0999]: type invariant may not hold` (or any `error[...]`) => the program FAILED verification.
- a `summary. N functions processed ...` line with NO `error` lines above it => the program VERIFIED.
The toolchain is already built, so the first run is fast; after you EDIT checker source the next run recompiles incrementally (~30-90s). Both `flux_rs::` and `flux::` attribute syntax work in test programs.

2. **Differential narrowing.** Propose competing hypotheses for the root cause and design *decisive, cheap, reversible* perturbations — minimal variant programs that change ONE structural dimension at a time — then classify each result's trajectory (convergent / divergent / oscillatory / chaotic). Illustrative dimensions worth isolating: the *sort* of the refinement component being updated (an abstract function sort like `hdl get: int -> bool` vs a plain `int` component); the *number* of components in the composite; whether the mutated field is reached through a `&mut` field-borrow vs a direct `&strg` argument; whether the setter actually *changes* the refinement or leaves it identical; nesting depth. The point is to find the smallest set of conditions under which the bug fires vs does not. Each kill condition (a perturbation that does NOT reproduce) names the next hypothesis — follow that edge.
3. **Root cause.** Trace/dump the actual constraint the checker emits and localize exactly WHERE the callee's post-call state is dropped on the field-borrowed place. Label each node's reasoning mode — abduction (proposed), deduction (traced from code), induction (ran and measured) — and keep confidence tied to mode.

Because you diagnosed by perturbation, your fix must handle every variant your differential narrowing showed is the SAME bug — verify each of those variant programs now passes.

6. **Regression.** Run the abstract-refinement suite; nothing previously green may go red.
